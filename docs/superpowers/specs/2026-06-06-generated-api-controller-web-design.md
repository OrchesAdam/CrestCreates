# Generated API Controller Web Design

## Purpose

CrestCreates should keep the familiar authoring experience of traditional API controller projects while moving the maintained runtime path to source-generated Minimal API endpoints.

The design goal is:

- Preserve controller-like API organization for application developers.
- Remove MVC controller runtime as the primary API execution path.
- Keep Dynamic API AoT-friendly and generated by `CrestCreates.CodeGenerator`.
- Let `CrestCreates.Web` reduce host boilerplate without hiding application-owned choices.

## Current Context

`SaaSHelpdesk.Web/Program.cs` currently registers many framework services directly:

- logging and audit logging;
- OpenAPI;
- OpenIddict and authentication;
- authorization, identity, permissions, settings, features, tenants;
- event bus and domain events;
- Dynamic API application service assemblies;
- middleware and endpoint mapping.

Some of this is framework default setup and should become a Web preset. Some is application-specific and must remain explicit.

`CrestCreates.Web` already has the right top-level shape:

```csharp
builder.AddCrestWeb();
app.UseCrestWeb();
app.MapCrestWeb();
```

But it should be redesigned as a framework Web preset and generated API facade, not as an MVC controller host.

## Architecture

The new API stack has four layers:

```text
CrestCreates.CodeGenerator
  Generates endpoint descriptors, endpoint providers, and Minimal API mapping code.

CrestCreates.DynamicApi
  Owns descriptors, route conventions, override semantics, endpoint capability model,
  generated registry, and runtime helpers.

CrestCreates.AspNetCore
  Bridges Dynamic API to ASP.NET Core endpoint routing.

CrestCreates.Web
  Provides host presets and user-friendly generated API configuration.
```

`CrestCreates.Web` must not become a runtime controller framework. Its job is to make the generated endpoint model feel natural to application developers.

## Authoring Model

Application developers may write controller-like classes:

```csharp
[GeneratedApiController]
[Route("api/tickets")]
public partial class TicketApi : CrestApiController
{
    [ApiOverride(CrudAction.GetList)]
    public Task<PagedResultDto<TicketDto>> GetListAsync(TicketListInput input)
    {
        return Service.GetListAsync(input);
    }

    [HttpPost("{id}/assign")]
    public Task<TicketDto> AssignAsync(Guid id, AssignTicketDto input)
    {
        return Service.AssignAsync(id, input);
    }
}
```

This preserves the shape of an API controller, but it is not an MVC controller:

- no MVC controller discovery;
- no MVC action invoker;
- no runtime reflection scanner as the default path;
- no dependency on `ControllerBase`.

The source generator reads this authoring model and emits Minimal API endpoint mappings.

## Compatibility Levels

Controller compatibility is intentionally scoped.

### Level 1: Naming Compatibility

Common CRUD method names map to conventional endpoints:

- `GetAsync`
- `GetListAsync`
- `CreateAsync`
- `UpdateAsync`
- `DeleteAsync`

These names can override generated CRUD endpoints when explicitly marked with `ApiOverride`.

### Level 2: Attribute Compatibility

Support a small, AoT-safe subset of familiar attributes:

- `Route`
- `HttpGet`
- `HttpPost`
- `HttpPut`
- `HttpDelete`
- `Authorize`
- `AllowAnonymous`
- `ProducesResponseType`

The generator interprets these attributes at compile time and writes endpoint metadata into generated code.

### Level 3: Helper Base Class

Provide a lightweight base class such as `CrestApiController`.

It may expose convenience helpers and context services, for example:

- `CurrentUser`
- `CurrentTenant`
- `Ok`
- `NotFound`
- `NoContent`

It must not inherit from MVC `ControllerBase`.

## Override and Extension Model

Generated CRUD endpoints support three behaviors:

```text
Keep
  Use the default generated endpoint.

Replace
  A user method replaces the default endpoint, for example custom GetList.

Extend
  A user convention adds metadata, filters, permissions, OpenAPI metadata,
  rate limits, cache policy, or other endpoint capabilities.
```

The core concepts should live in `CrestCreates.DynamicApi`:

- `DynamicApiEndpointDescriptor`
- `DynamicApiEndpointConventionContext`
- `IDynamicApiEndpointConvention`
- `ApiOverrideAttribute`
- `GeneratedApiControllerAttribute`

Descriptors are generated. Conventions consume generated descriptors. Runtime reflection must not be required to discover endpoints.

## Web Preset Design

`CrestCreates.Web` should preserve the normal ASP.NET Core host shape:

```csharp
var builder = WebApplication.CreateBuilder(args);

builder.AddCrestWeb<HelpdeskWebModule>(options =>
{
    options.UseOpenIddict();
    options.UseGeneratedApi(api =>
    {
        api.AddApplicationServiceAssembly<TicketAppService>();
        api.AddApplicationServiceAssembly<CustomerAppService>();
    });
});

builder.Services.AddAuthentication()
    .AddCustomerApiKey();

builder.Services.AddValidatorsFromAssemblyContaining<CreateTicketDtoValidator>();
builder.Services.AddSettingDefinitionProvider<HelpdeskSettingDefinitionProvider>();

var app = builder.Build();

app.UseCrestWeb();
app.MapCrestWeb();

await app.InitializeCrestAsync();

app.Run();
```

The user still sees familiar ASP.NET Core phases:

- configure builder;
- register app-specific services;
- build app;
- configure middleware;
- map endpoints;
- initialize modules;
- run.

The framework hides repeated platform defaults, not application intent.

## What CrestCreates.Web Should Abstract

`AddCrestWeb` may configure:

- Serilog and Crest logging;
- audit logging services;
- default OpenAPI;
- default OpenIddict server/authentication;
- exception handling;
- authorization platform services;
- identity, permission, setting, feature, and tenant platform services;
- local event bus and domain event defaults;
- generated Dynamic API registration entry points.

`UseCrestWeb` may configure:

- request logging;
- exception handling;
- audit logging;
- routing-sensitive middleware order;
- multitenancy;
- authentication;
- tenant boundary;
- authorization.

`MapCrestWeb` may configure:

- OpenIddict endpoints;
- generated Dynamic API endpoints;
- OpenAPI endpoints.

`InitializeCrestAsync` may wrap module initialization and make the startup lifecycle discoverable.

## What CrestCreates.Web Should Not Abstract

These remain application-owned:

- custom authentication schemes such as customer API key authentication;
- application validators;
- application setting and feature definition providers;
- application DbContext, repository, migration, and seeding details;
- application data seeders;
- custom module configuration;
- startup diagnostics and application-specific console output;
- custom endpoint implementations such as overridden `GetListAsync`.

## Migration Strategy

Because the framework is not final, breaking changes are allowed, but they should be staged.

1. Add the generated API controller authoring model.
2. Generate Minimal API endpoints from controller-like classes.
3. Add Web preset options for generated API configuration.
4. Move samples such as SaaSHelpdesk to the new preset.
5. Remove `ApiControllerBase` from `CrestCreates.Web` as a recommended surface.
6. Mark MVC controller generators as legacy or remove them after generated endpoint parity is verified.

Do not delete existing controller-related code before the generated API controller path is usable in a sample.

## Testing Strategy

Tests should express the maintained mainline:

- generated endpoint mapping is used;
- controller-like classes do not require MVC runtime discovery;
- `ApiOverride(CrudAction.GetList)` replaces default generated `GetList`;
- endpoint conventions add metadata without runtime scanning;
- `SaaSHelpdesk.Web` can run with short `AddCrestWeb`/`UseCrestWeb`/`MapCrestWeb` host setup;
- OpenAPI metadata remains correct for generated endpoints.

Legacy MVC controller tests should not be expanded unless they protect an explicitly retained compatibility surface.

## Non-Goals

This design does not attempt to fully clone MVC.

The following are not primary goals:

- `ControllerContext`;
- `ModelState`;
- MVC action filters;
- runtime controller discovery;
- runtime reflection endpoint execution;
- complete MVC model binding parity.

If an application needs full MVC behavior, it should opt into ASP.NET Core MVC separately. CrestCreates generated API remains the AoT-first framework path.

## Design Decision

`CrestCreates.Web` becomes the ergonomic Web facade.

`CrestCreates.DynamicApi` remains the generated API core.

The public story becomes:

```text
Write APIs in a controller-like style.
CrestCreates generates Minimal API endpoints at compile time.
Configure common platform defaults through CrestCreates.Web.
Keep application-specific choices explicit.
```
