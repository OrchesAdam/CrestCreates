# Agent/MCP Tool JSON Contract Root Unification Design

- **Date**: 2026-07-27
- **Status**: APPROVED
- **Approved for implementation**: 2026-07-27
- **Issue**: [#62 — tech-debt: Unify Agent/MCP Tool JSON contract roots](https://github.com/OrchesAdam/CrestCreates/issues/62)
- **Depends on**: [#58 — Control Plane JSON Contract Root Generation](./2026-07-24-control-plane-json-contract-root-generation-design.md)

## 1. Goal

Issue #62 removes the remaining double-maintained JSON binding-root lists from
the first-party Agent Memory Tool and MCP Memory Tool projections.

The only supported root-definition mainline becomes:

```text
handwritten AgentToolSpec / McpToolSpec InputType + OutputType
        ↓
CrestCreates.JsonContracts.Build semantic Tool-Spec adapter
        ↓
generated JsonSerializable attributes + immutable BindingRootTypes manifest
        ↓
official System.Text.Json Source Generator
        ↓
existing handwritten Agent/MCP contributor and resolver composition
```

The build task generates direct JSON roots. The official STJ generator remains
the only component that generates `JsonTypeInfo<T>`. Contributors retain their
runtime identity and composition responsibilities, but no longer repeat the
binding-root types in a second array or set.

## 2. Repository facts and migration inventory

The repository contains exactly three externally bound first-party Tool JSON
ownership boundaries:

| Boundary | Context owner | Spec owner before #62 | Contributor owner | Action |
|---|---|---|---|---|
| Control Plane | `Agent.ControlPlane.Abstractions` | service interfaces | none in #58 | already migrated by #58 |
| Agent Memory Tool | `Agent.Memory.Tools.Abstractions` | `Agent.Memory.Tools` | `Agent.Memory.Tools` | migrate in #62 |
| MCP Memory | `CrestCreates.Mcp.Memory` | same assembly | same assembly | migrate in #62 |

Other Agent JSON contexts are authoring, LLM, prompting, persistence, or
internal provider contexts. They are not contributor-owned externally bound
Tool projections and are outside this issue.

### 2.1 Agent Memory roots

`AgentMemoryToolSpecifications` contains seven `[AgentToolSpec]` declarations.
Their exact input/output pairs are the fourteen binding roots currently copied
into both:

- `AgentMemoryToolJsonSerializerContext` attributes; and
- `AgentMemoryToolJsonContextContributor.Roots`.

Nested DTOs and enums currently listed on the Context are STJ transitive
metadata, not independent binding roots.

### 2.2 MCP Memory roots

`McpMemoryTools` contains four `[McpToolSpec]` declarations. They produce six
unique roots because the two expand tools share the same input/output pair.
Those roots are currently copied into both the Context and Contributor. The
binding-key to `JsonTypeInfo` mapping remains an explicit runtime contract and
is not generated by this issue.

## 3. Architectural boundary

This issue owns:

- semantic adapters for `[AgentToolSpecs]`/`[AgentToolSpec]` and
  `[McpToolSpecs]`/`[McpToolSpec]`;
- a common direct-root model containing binding-root provenance;
- generated immutable `BindingRootTypes` manifests;
- Agent Memory and MCP Memory migrations;
- removal of their handwritten direct-root arrays and Context attributes;
- repository guards preventing the double-maintenance pattern from returning;
- wire/parity/composition and NativeAOT publish-link-run evidence.

This issue does not own:

- BuildTask transport, path, incremental, or Global Usings redesign from #58;
- runtime reflection or assembly scanning;
- contributor discovery or automatic registration;
- contributor identity, ordering, module selection, or resolver ordering;
- MCP binding-key generation;
- nested CLR metadata ownership changes;
- internal persistence/provider/LLM/authoring Context migration;
- a reflection serializer fallback;
- Tool DTO projection generation.

## 4. Authoritative declarations

### 4.1 Tool-Spec surface adapter

`JsonContractSurfaceAttribute` remains the single Context marker. Its target
may now be one of three supported semantic shapes:

1. a closed interface, using the #58 method-signature adapter;
2. a class marked `[AgentToolSpecs]`, using nested `[AgentToolSpec]`
   `InputType` and `OutputType` values;
3. a class marked `[McpToolSpecs]`, using nested `[McpToolSpec]`
   `InputType` and `OutputType` values.

Adapter selection is semantic and exact by attribute metadata identity. It is
not based on class names, namespace prefixes, source text, or reflection.
Unsupported target shapes continue to fail with `CJC002`.

All adapters produce the same `JsonContractRootModel`. Tool-Spec roots also
carry binding provenance:

```text
adapter kind
container metadata name
spec metadata name
InputType or OutputType role
```

### 4.2 Agent declaration ownership

The Agent Memory Context lives in `Agent.Memory.Tools.Abstractions`, while the
Contributor lives in `Agent.Memory.Tools`. A partial Context cannot be extended
from another assembly, so the authoritative Tool-Spec declaration must be
visible to the Context-owning compilation.

`AgentMemoryToolSpecifications` and its public capability-id constants move to
`Agent.Memory.Tools.Abstractions`. This is a declaration-layer move, not a
second copy. The implementation assembly continues to own handlers, runtime
composition, contributor registration, and concrete descriptor-registry
registration.

The previous runtime assembly emits type forwarders for the moved public outer
declaration types. CLR nested identities resolve through the forwarded outer
type and cannot be forwarded individually. Existing binaries must not fail
merely because ownership moved to the lower assembly.

The Agent Tool source generator gains an explicit container option that omits
the concrete `DescriptorProviderRegistry` module initializer while retaining:

- generated descriptor provider;
- generated exact typed bindings;
- JSON contract registry registration.

The upper runtime assembly explicitly registers the generated descriptor
provider. This prevents an Abstractions project from referencing the concrete
Metadata registry and preserves the repository dependency direction.

The generated provider remains internal and is shared only with the paired
runtime assembly through `InternalsVisibleTo`; no new public runtime API is
introduced for test convenience.

### 4.3 MCP declaration ownership

`McpMemoryTools`, `McpMemoryJsonSerializerContext`, and
`McpMemoryJsonContextContributor` already share one assembly. No ownership move
or new registration path is required.

## 5. Root model and generated manifest

Each Context model contains four deterministic sets:

```text
SurfaceRootTypes  = roots from all supported marked surfaces
BindingRootTypes  = roots specifically from Agent/MCP Tool-Spec adapters
ExplicitRootTypes = handwritten JsonContractExplicitRoot extras
AllDirectRootTypes = SurfaceRootTypes union ExplicitRootTypes
```

For a Context using only Tool-Spec surfaces, `BindingRootTypes` equals
`SurfaceRootTypes`. Interface-derived roots remain Surface roots but are not
automatically called Binding roots.

The generated manifest remains nested beside the generated partial Context:

```csharp
public partial class AgentMemoryToolJsonSerializerContext
{
    public static class RootManifest
    {
        public static IReadOnlySet<Type> BindingRootTypes => ...;
    }
}
```

The public property returns a `FrozenSet<Type>` instance behind the read-only
interface. It must not be downcastable to `HashSet<Type>`; if the runtime
exposes an `ISet<Type>` compatibility view, every mutation attempt must throw
`NotSupportedException` and leave the set unchanged.

Manifest accessibility remains project-configured:

- Agent Memory: `Public`, because its Contributor is in another assembly;
- MCP Memory: `Internal`, because its Contributor is in the same assembly;
- Control Plane: unchanged `Internal` behavior from #58.

The task never promotes accessibility automatically.

## 6. Semantic rules

1. Traverse every nested Tool spec declaration accepted by the owning Tool
   generator.
2. Read only exact `InputType` and `OutputType` named arguments.
3. A missing input or output type contributes no root for that role.
4. Normalize nullable annotations consistently with #58.
5. Deduplicate exact constructed symbols with `SymbolEqualityComparer.Default`.
6. Do not expand properties, collections, enum members, or nested DTO graphs.
7. Preserve provenance for every spec/role that contributed a shared root.
8. Sort Contexts, roots, and provenance with ordinal comparison before writing.
9. Reject ErrorType, open generic, pointer, function-pointer, ref-like, or
   inaccessible root shapes using the existing `CJC004`-`CJC007` contract.
10. Do not reinterpret Tool names, capability IDs, binding keys, or schema IDs.
11. Removing a spec declaration must remove its now-unowned generated root on
    the next build through the #58 input-manifest/stamp chain.
12. STJ remains authoritative for transitive metadata and unsupported JSON
    shapes.

## 7. Runtime invariants

1. Agent contributor `Id`, `Order`, and `ModuleId` remain exactly
   `agent-memory-tools`, `200`, and `agent-memory-tools`.
2. MCP contributor ID remains `mcp-memory`.
3. MCP binding keys and their exact `JsonTypeInfo` mappings do not change.
4. Existing module opt-in behavior does not change.
5. Existing root ownership validation remains authoritative.
6. Existing resolver-chain order, options profile, converter behavior, and
   freezing do not change.
7. Every generated binding root has a source-generated `JsonTypeInfo`.
8. Every enabled binding root has exactly one contributor owner.
9. Nested metadata may legitimately exist in multiple Contexts when parity
   validation remains green.
10. No `DefaultJsonTypeInfoResolver`, `Assembly.GetTypes`, or reflection
    fallback is introduced.

### 8.2 Boundary

| ID | Case | Expected |
|---|---|---|
| B01 | Same root used by multiple specs | one generated attribute/root, all provenance retained |
| B02 | Nested DTO property added | direct Binding manifest unchanged; STJ closure updates |

| B05 | MCP internal manifest | same assembly consumes it; external assembly cannot |
| B06 | Interface and Tool-Spec surfaces coexist | Surface union stable; Binding set contains only Tool-Spec roots |

## 10. Migration order

1. Freeze existing root, contributor identity, binding-key, wire, and AOT
   behavior with acceptance tests.
2. Extend the common BuildTask model and writer with Binding roots.
3. Add Agent/MCP Tool-Spec semantic adapters and failure coverage.
4. Move the Agent declaration boundary down without adding a concrete Metadata
   dependency to Abstractions.
5. Migrate the Agent Context, enable Public manifest, and consume it from the
   Contributor.
6. Migrate MCP Context and Contributor while preserving explicit key mappings.
7. Enable repository enforcement and run both native fixtures.

## 11. Exit criteria

- The fourteen Agent Memory binding roots and six unique MCP Memory binding
  roots come only from their existing Tool spec declarations.
- Neither migrated Context handwrites `[JsonSerializable]` binding roots.
- Neither production Contributor contains a handwritten binding-root array or
  set.
- Contributors consume immutable generated `BindingRootTypes` manifests.
- Contributor identity, ordering, module selection, MCP binding keys, resolver
  composition, schema parity, and JSON wire shapes remain unchanged.
- All approved acceptance tests execute without `Skip`.
- Agent Memory and MCP Memory NativeAOT fixtures publish, link, and run their
  original native binaries successfully.
- Repository enforcement prevents the duplicate-root pattern from returning.
