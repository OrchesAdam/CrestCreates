## 1. Decision Summary

Phase 9b+ closes one production gap in the Agent Tool governance mainline:

```text
durable pre-dispatch checkpoint may have committed
    + acknowledgement may have been lost
    + current Worker must not guess
    -> recover by durable Attempt identity
    -> compare the complete checkpoint
    -> preserve the invocation fence
    -> either continue the same live ownership once or close safely
    -> never replay a Tool merely to discover state
```

The public recoverability direction is fixed as:

```text
AgentToolLogicalInvocationKey + AttemptId
    -> GetPreDispatchStateAsync
    -> Missing | Accepted(checkpoint snapshot, original receipt)
```

Caller-generated `AuditId` is rejected as the primary direction. A random ID
generated by the caller would itself need a durable write before checkpoint
acceptance; without that write it only moves the acknowledgement-loss window.
The existing Phase 8f authority is already logical invocation plus Attempt, and
the current in-memory auditor already enforces that identity.

`AuditId` remains the immutable identity of the first accepted governance
checkpoint. The provider allocates it once. Identical Record retries and lookup
return the same `AuditId` and original `AcceptedAt`.

The protocol also closes a second, less visible gap: a durable Invocation Gate
must know that a pre-dispatch write may be in flight before the write starts.
Otherwise process death plus lease expiry could expose a replacement Attempt
while the old checkpoint exists. Therefore the mainline gains an explicit
`PreDispatchPending -> PreDispatchReady -> PreDispatchAccepted` publication
fence.

The resulting mainline is:

```text
Acquire invocation lease
    -> claim approval
    -> Gate.PreparePreDispatchIntent(Pending)
    -> reserve/query budget by Attempt identity
    -> Gate.BindPreDispatchReservation(Ready)
    -> Auditor.RecordPreDispatch
    -> Gate.BindAcceptedPreDispatch(Accepted receipt)
    -> Gate.TryMarkDispatchStarted(exact receipt)
    -> Dispatcher
```

Any ambiguous write or bind result is resolved by read/CAS reconciliation. No
parallel legacy path, caller-AuditId fallback, volatile side dictionary, or
Accountability-driven dispatch path is introduced.

## 2. Problem and Repository Facts

### 2.1 Phase 8f already fails closed

`AgentToolInvoker` writes `AgentToolGovernancePreDispatchRecord` after approval
and budget reservation and before `TryMarkDispatchStartedAsync`. If the first
write fails ambiguously, it retries the same full record once. When both calls
remain unconfirmed, it releases the business budget, marks the logical
invocation `Indeterminate`, calls Dispatcher zero times, and does not abandon
the lease.

This is the correct fail-closed behavior for one process. It is not yet a
durable recovery protocol.

### 2.2 The current interface hides accepted pre-dispatch state

`IAgentToolGovernanceAuditor` can query finalization by `AuditId`, but cannot
query a possible accepted pre-dispatch checkpoint by the identities the caller
still knows after response loss:

```text
LogicalInvocationKey
AttemptId
```

The current in-memory implementation indexes pre-dispatch records by this exact
pair and therefore demonstrates the intended semantic identity. The production
contract does not expose that fact.

### 2.3 Lease expiry can reopen an unresolved window

Phase 8f allows an expired pre-dispatch lease to be replaced when
`DispatchStarted` is false. That is safe only when no required governance
checkpoint may have been accepted. Once a Worker has begun an ambiguous durable
checkpoint write, expiry alone is not proof of absence.

The Invocation Gate needs a durable pre-dispatch pending marker before budget
reservation. Pending, Ready, and Accepted attempts remain fenced across expiry
and restart until explicit reconciliation.

### 2.4 Budget and checkpoint state are independent

The existing Invoker may prove that its own Worker never called Dispatcher and
release the budget while still being unable to prove whether the checkpoint was
accepted. This state is valid:

```text
Checkpoint = unknown to caller, possibly Accepted
Budget     = Released
Invocation = Indeterminate
Dispatch   = not started by this Worker
```

Recovery must inspect and compare these independent authorities. It must not
infer checkpoint state from budget state or vice versa.

### 2.5 Accountability is post-fact

Phase 9a explicitly keeps Agent Tool Governance Audit as an execution-control
protocol. `IAuditRecorder` may record the result of reconciliation after the
control transition, but an Accountability sink receipt cannot authorize,
release, or dispatch a Tool.

### 2.6 Phase 9b provides the provider kernel, not this protocol

The implemented Phase 9b PostgreSQL provider supplies direct Npgsql access,
checksummed migrations, explicit tenant scope, transaction/session mechanics,
restart tests, crash-worker orchestration, and native publish-and-run evidence.
It deliberately excluded Agent Tool pre-dispatch reconciliation. Phase 9b+
extends that provider without redefining its transaction or migration kernel.

## 3. Boundary

### 3.1 In scope

- One recoverable pre-dispatch identity:
  `AgentToolLogicalInvocationKey + AttemptId`.
- Typed Record outcomes: Accepted, Duplicate, and Conflict.
- Read-only `GetPreDispatchStateAsync` returning authoritative Missing or an
  immutable Accepted checkpoint plus its original receipt.
- Complete checkpoint equality and conflict detection.
- Durable acceptance receipt with stable `AuditId` and first `AcceptedAt`.
- Invocation Gate `PreDispatchPending`, `PreDispatchReady`, and
  `PreDispatchAccepted` fences.
- A Pending intent before budget reservation, so reserve-response loss and a
  crash before ReservationId reaches the Gate cannot reopen the Attempt.
- Budget reservation idempotency and lookup by the same pre-dispatch Attempt
  identity; ReservationId remains the accepted reservation identity, not the
  recovery key.
- Dispatch-start transition bound to the exact accepted receipt, lease,
  fencing token, and reservation.
- Provider-neutral Gate and Budget state reads required for reconciliation.
- Immediate same-Worker acknowledgement-loss recovery.
- Restart/background reconciliation of pre-dispatch `Indeterminate` Attempts.
- Explicit rules for authoritative Missing, Accepted, Conflict, stale fencing,
  incompatible budget state, cancellation, and concurrent reconcilers.
- PostgreSQL durable Gate, Budget, governance checkpoint, and reconciliation
  state necessary to execute this protocol across process restart.
- Complete PostgreSQL implementations of the existing
  `IAgentToolInvocationGate`, `IAgentToolBudgetGate`, and
  `IAgentToolGovernanceAuditor` surfaces. A production registration cannot mix
  durable pre-dispatch methods with volatile completion/release/decision paths.
- Full-semantic in-memory implementations used for development and shared
  contract cases, without a durability claim.
- Safe post-fact Accountability projection of reconciliation results.
- Retention and cleanup rules covering all participating records.
- Generated JSON contracts and real PostgreSQL NativeAOT publish-link-run
  evidence.
- Runner-free shared Contract Cases and concrete in-memory/PostgreSQL test
  runners.

### 3.2 Out of scope

- Agent Memory persistence or recovery (#55).
- Transactional Outbox or reliable delivery generalization (#25).
- Automatic Tool replay after a call has returned `Indeterminate`.
- Exactly-once external side effects.
- Inferring a business result after `DispatchStarted` may be true.
- Replacing Agent Tool Governance Auditor with Accountability `IAuditSink`.
- A general approval workflow, approval UI, or HumanTask approval product.
- A general cross-application budget product.
- Cross-provider distributed transactions.
- Arbitrary cross-tenant reconciliation queries.
- Control Plane self-approval or direct Runtime Handler execution.
- A second caller-generated `AuditId` compatibility path.
- A reflection JSON fallback, open object payload, or provider type in Runtime
  abstractions.

### 3.3 Compatibility position

This is a mainline contract cutover. The following are not retained as two
equivalent production paths:

- `RecordPreDispatchAsync` returning an unclassified handle;
- dispatch-start without an accepted pre-dispatch receipt;
- lease expiry reopening a Pending, Ready, or Accepted Attempt;
- provider-specific lookup hidden behind retrying Record forever;
- conflict represented only by an arbitrary provider exception.

Development in-memory implementations remain supported, but must implement the
same observable protocol and advertise no restart/cross-node durability.

## 4. System Invariants

### INV-01 — One recoverable identity

`AgentToolLogicalInvocationKey + AttemptId` is the only public pre-dispatch
recovery identity. `AuditId`, `LeaseId`, `ReservationId`, CorrelationId, and
Capability idempotency keys never substitute for it.

### INV-02 — Receipt identity is immutable

The first durable acceptance allocates one `AuditId` and one `AcceptedAt`.
Identical sequential retries, concurrent retries, lookup, and restart recovery
return those original values.

### INV-03 — Full checkpoint conflict safety

For one recovery identity:

```text
no checkpoint                         -> Accepted
same complete checkpoint              -> Duplicate
different complete checkpoint         -> Conflict
```

Conflict never overwrites the first checkpoint. A hash may accelerate compare
or aid diagnostics, but equality of a hash alone is not authoritative.

### INV-04 — Complete means complete

Conflict comparison includes every dispatch-authorizing fact:

- full logical invocation identity and AttemptId;
- invocation fingerprint, arguments-evaluated flag/hash, call origin, and roles
  hash;
- Tool, Capability, InputSchema, and OutputSchema contract identities;
- complete effective governance;
- LeaseId, AttemptId, FencingToken, AcquiredAt, and ExpiresAt;
- approval decision, claim state, EvidenceId, approver-safe reference, and
  stable reason;
- ReservationId, AttemptId, fingerprint, category, units, limit, and state.

No field may silently default during migration or deserialization.

### INV-05 — Boundary snapshots are detached

Checkpoint write and read boundaries deep-snapshot all nested records and
collections. A caller mutation after Record and a reader mutation after lookup
cannot alter durable equality or later reads.

### INV-06 — Pending intent precedes budget reservation

Before budget reservation can begin, the Invocation Gate stores
`PreDispatchPending` with the exact lease, invocation fingerprint, and claimed
approval facts. Pending survives lease expiry and process restart and blocks
abandon, replacement Attempt, and business dispatch. This fence makes an
ambiguous budget reserve recoverable by Attempt identity.

### INV-07 — Accepted is a durable fence

After an exact reservation is recovered/bound, the Gate becomes
`PreDispatchReady`; only Ready may write the checkpoint. After acceptance, the
Gate binds the original receipt. Ready and Accepted Attempts block replacement
until explicitly reconciled or, for Accepted, atomically marked DispatchStarted.

### INV-08 — Dispatch requires exact accepted proof

`TryMarkDispatchStartedAsync` succeeds only for the current complete lease,
fencing token, ReservationId, and accepted `AuditId`. It is idempotent for the
same proof and rejects stale, missing, or conflicting proof.

The lease snapshot frozen by `PreparePreDispatchIntent` is immutable checkpoint
content. Lease renewal advances a separate Gate-owned `CurrentExpiresAt`; it
does not rewrite the frozen `AcquiredAt`/prepared expiry or create a checkpoint
conflict. Dispatch still requires the current lease to be unexpired.

### INV-09 — Ambiguity never opens the gate

Provider failure, timeout, cancellation, unknown lookup result, bind-response
loss, stale lease, or context mismatch leaves the Attempt fenced. It cannot
cause abandon, replacement, or dispatch.

### INV-10 — Authoritative Missing is stronger than absence observed by caller

`Missing` may be returned only by a consistent read from the same durable
authority while retention guarantees the row could not have been removed.
Provider unavailability, replica lag, schema mismatch, timeout, or cleanup race
must throw/fail and must not be translated to Missing.

### INV-11 — Same-Worker continuation is narrow

Immediate recovery may continue toward dispatch only when the same active
Worker still owns an unexpired exact lease, the checkpoint is an exact Accepted
match, Gate binding is confirmed, approval remains the claimed result for that
Attempt, and the reservation is still Reserved and exact.

### INV-12 — Restart reconciliation never auto-dispatches

Once an invocation returned `Indeterminate`, ownership was lost, or recovery
crossed a process boundary, reconciliation never invokes Dispatcher. It may
close an Attempt only when all authorities prove business dispatch did not
start; otherwise it preserves `Indeterminate`.

### INV-13 — Budget transitions are exactly-once semantic transitions

Reconciliation reads the exact reservation and performs one idempotent CAS to
Released when safe. Duplicate/concurrent reconciliation returns the existing
terminal receipt. It never creates a replacement reservation or charges/releases
capacity twice.

### INV-14 — Reconciliation is CAS and monotonic

Only one reconciler wins a state transition. Repeated requests return the same
terminal result. Released, DispatchStarted, Completed, and terminal
Indeterminate states cannot be rewritten into one another.

`StillPending` is a retryable reconciliation observation, not an immutable
terminal receipt. It may update bounded attempt/revision/last-observed metadata
and later progress to Released or another terminal result. Once a terminal
reconciliation receipt exists, it is immutable and every repeated/concurrent
request returns that receipt.

### INV-15 — Tenant scope is exact

Tenant identity is part of every lookup, unique key, foreign key, receipt, and
cleanup query. Host `TenantId == null` means exact host scope, never wildcard.

### INV-16 — Retention protects live reconciliation

No cleanup may remove Gate, Attempt, Budget, checkpoint, finalization, or
reconciliation state while any linked Attempt is PreDispatchPending,
PreDispatchReady, PreDispatchAccepted, ReleasePending, CompletionPending, or
Indeterminate, or before the configured maximum reconciliation window has
elapsed.

### INV-17 — Accountability cannot drive control

Accountability projection happens after the governance transition. Its failure
cannot roll back, reopen, release, dispatch, or reclassify that transition.

### INV-18 — No business replay as a probe

No path calls Dispatcher to determine whether a checkpoint existed or whether
a prior Tool execution happened. A post-dispatch unknown remains outside this
pre-dispatch reconciler.

### INV-19 — Provider claims match executable evidence

InMemory is full-semantic/dev only. PostgreSQL may claim durable pre-dispatch
reconciliation only after restart, crash-window, concurrency, tenant isolation,
retention, migration, and native publish-link-run cases pass.

### INV-20 — Generated contracts are the only JSON path

Durable checkpoint and receipt serialization uses source-generated
`JsonTypeInfo`. No reflection resolver, untyped polymorphism, `object?` payload,
or new trimming suppression is permitted.

### INV-21 — Confirmed budget denial is Attempt-scoped and replay-safe

A structurally valid budget Denied result is a confirmed control outcome, not
Indeterminate. It publishes one immutable `Abandoned` Attempt receipt carrying
the stable safe denial outcome/reason and calls Dispatcher zero times. The Gate
receipt is the authority for Attempt terminal state and later Acquire
availability; an accepted Governance Decision record is the immutable evidence
for why the Attempt was denied.

The logical invocation remains bound to its original fingerprint but is not
logically Completed. A later Acquire with the same fingerprint creates a new
Attempt and re-evaluates approval/budget; it does not replay the old denial as a
logical terminal result. A different fingerprint remains Conflict. Repeating
the same denial publication returns the original Abandoned receipt; changed
denial content conflicts.

## 5. Public Contract Direction

The type names below are normative in responsibility and shape. The
Implementation Plan may refine file layout, but it must not change the selected
identity, statuses, or state-machine semantics.

### 5.1 Recovery identity

```csharp
public readonly record struct AgentToolPreDispatchIdentity(
    AgentToolLogicalInvocationKey LogicalInvocationKey,
    string AttemptId);
```

Validation reuses `AgentToolGovernanceGuard` and requires a non-empty AttemptId.
String comparison is ordinal. Tenant scope remains inside the logical key.

### 5.2 Receipt

Replace the generic `AgentToolGovernanceAuditHandle` with one semantic type:

```csharp
public sealed record AgentToolGovernancePreDispatchReceipt
{
    public required AgentToolPreDispatchIdentity Identity { get; init; }
    public required string AuditId { get; init; }
    public required DateTimeOffset AcceptedAt { get; init; }
}
```

There is no parallel Handle/Receipt production API. Finalization continues to
use the accepted `AuditId` from this receipt.

### 5.3 Typed write result

```csharp
public enum AgentToolGovernancePreDispatchWriteStatus
{
    Unknown = 0,
    Accepted = 1,
    Duplicate = 2,
    Conflict = 3
}

public sealed record AgentToolGovernancePreDispatchWriteResult
{
    public required AgentToolGovernancePreDispatchWriteStatus Status { get; init; }
    public AgentToolGovernancePreDispatchReceipt? Receipt { get; init; }
}
```

Rules:

- Accepted and Duplicate require an exact receipt.
- Conflict carries no dispatch-authorizing receipt.
- Unknown is never a successful return.
- provider availability/timeout/cancellation remains an exception or cancelled
  operation, not Conflict or Missing.

`RecordPreDispatchAsync` becomes:

```csharp
ValueTask<AgentToolGovernancePreDispatchWriteResult> RecordPreDispatchAsync(
    AgentToolGovernancePreDispatchRecord record,
    CancellationToken cancellationToken = default);
```

### 5.4 Read result

```csharp
public enum AgentToolGovernancePreDispatchReadStatus
{
    Unknown = 0,
    Missing = 1,
    Accepted = 2
}

public sealed record AgentToolGovernancePreDispatchReadResult
{
    public required AgentToolGovernancePreDispatchReadStatus Status { get; init; }
    public AgentToolGovernancePreDispatchReceipt? Receipt { get; init; }
    public AgentToolGovernancePreDispatchRecord? Checkpoint { get; init; }
}
```

Accepted requires both Receipt and a detached complete Checkpoint. Missing
requires both null. Unknown is invalid as a returned provider result.

`IAgentToolGovernanceAuditor` gains:

```csharp
ValueTask<AgentToolGovernancePreDispatchReadResult> GetPreDispatchStateAsync(
    AgentToolPreDispatchIdentity identity,
    CancellationToken cancellationToken = default);
```

Lookup is not an administrative cross-tenant search API. The caller supplies one
exact identity already obtained from trusted invocation state.

### 5.5 Complete checkpoint equality

One runtime-owned comparator is the sole semantic authority:

```text
AgentToolGovernancePreDispatchComparer
    -> Equivalent(left, right)
    -> ValidateIdentity(record, identity)
```

InMemory, PostgreSQL, Invoker recovery, reconciler, and tests reuse the same
semantic projection or prove equivalent behavior through shared Contract Cases.
Provider SQL does not invent a narrower equality definition.

The provider may persist a deterministic internal integrity value for indexing
and diagnostics. On duplicate/conflict paths it must still compare or validate
the complete stored snapshot. Digest equality alone is insufficient.

### 5.6 Invocation Gate cutover

`IAgentToolInvocationGate` gains explicit pre-dispatch operations:

```csharp
ValueTask<AgentToolInvocationPreDispatchResult> PreparePreDispatchIntentAsync(
    AgentToolInvocationLease lease,
    AgentToolInvocationPreparePreDispatchIntentRequest request,
    CancellationToken cancellationToken = default);

ValueTask<AgentToolInvocationPreDispatchResult> BindPreDispatchReservationAsync(
    AgentToolInvocationLease lease,
    AgentToolInvocationBindReservationRequest request,
    CancellationToken cancellationToken = default);

ValueTask<AgentToolInvocationPreDispatchResult> BindAcceptedPreDispatchAsync(
    AgentToolInvocationLease lease,
    AgentToolInvocationBindPreDispatchRequest request,
    CancellationToken cancellationToken = default);

ValueTask<AgentToolInvocationPreDispatchResult> GetPreDispatchStateAsync(
    AgentToolPreDispatchIdentity identity,
    CancellationToken cancellationToken = default);
```

`PreparePreDispatchIntent` stores the full lease identity plus a detached
snapshot of `AgentToolGovernanceAuditContext` and the safe
`AgentToolApprovalResult` before budget reservation. The opaque approval input
is never stored. Repeated identical preparation is idempotent; changed data
conflicts. This intent is the restart authority used to validate every Context,
contract, governance, lease, and approval field in the later checkpoint.
Its returned result contains the frozen intent snapshot used to construct the
later checkpoint. Renewals update only Gate ownership expiry, not this snapshot.

`BindPreDispatchReservation` transitions Pending to Ready and stores the exact
ReservationId and reservation facts. It is idempotent for the same reservation
and conflicts on any changed identity/content. The Auditor may be called only
after Ready is confirmed.

`BindAcceptedPreDispatch` stores the exact receipt and permits only a matching
`PreDispatchReady` Attempt. A lost bind response is reconciled by Gate read.

`TryMarkDispatchStartedAsync` is cut over to accept the exact receipt and
reservation proof. The old receipt-free overload is removed from the mainline.

### 5.7 Budget reserve and read contract

One Attempt may own at most one budget reservation. `ReserveAsync` is
idempotent by `AgentToolPreDispatchIdentity` plus the complete budget request:

```text
no reservation                         -> Reserved(new ReservationId)
same Attempt + same complete request   -> Reserved(original ReservationId)
same Attempt + changed request         -> Conflict/fail closed
```

This requirement closes both reserve-response loss and process death before the
ReservationId is bound into the Invocation Gate.

`IAgentToolBudgetGate` gains a provider-neutral exact read:

```csharp
ValueTask<AgentToolBudgetReservationReadResult> GetReservationStateAsync(
    AgentToolPreDispatchIdentity identity,
    CancellationToken cancellationToken = default);
```

The returned reservation still carries ReservationId, AttemptId, and
InvocationFingerprint, all of which are validated before Gate binding or
finalization. Missing, Reserved, Released, Committed, and Indeterminate remain
distinct. Availability failure is not Missing. Finalize remains the only
terminal mutation API.

### 5.8 Reconciler

Runtime owns orchestration:

```csharp
public interface IAgentToolPreDispatchReconciler
{
    ValueTask<AgentToolPreDispatchReconciliationResult> ReconcileAsync(
        AgentToolPreDispatchIdentity identity,
        CancellationToken cancellationToken = default);
}
```

The returned observation distinguishes at least:

```text
Released             exact no-dispatch Attempt safely closed
AlreadyReleased      repeated reconciliation
StillPending         an authority is unavailable or not terminally provable
Conflict             durable authorities disagree
PostDispatchUnknown  dispatch may have started; outside this reconciler
Missing              no matching Invocation Attempt exists
```

The result is safe operational information. It is not a Tool output and never
contains raw arguments, approval payload, or arbitrary provider exceptions.

Reconciliation persistence separates retryable observations from terminal
receipts:

```text
Retryable observation
    StillPending
    transient provider unavailable
    retryable CAS/read loss
    mutable only as bounded last-observed/attempt/revision metadata

Immutable terminal receipt
    Released
    Conflict / terminal Indeterminate
    PostDispatchUnknown (terminal for this pre-dispatch reconciler)
```

`AlreadyReleased` is the replay projection of an existing Released receipt,
not a second receipt. `Missing` returns no receipt because no matching Attempt
aggregate exists. `StillPending` never blocks a later reconciliation from
progressing to a terminal receipt.

## 6. State Model

### 6.1 Independent authorities

```text
Logical Invocation
    Registered | Running | Completed | Indeterminate

Attempt
    Acquired
    PreDispatchPending
    PreDispatchReady
    PreDispatchAccepted
    DispatchStarted
    ReleasePending
    Released
    CompletionPending
    Completed
    Indeterminate
    Abandoned

Budget Reservation
    Reserved | Released | Committed | Indeterminate

Governance Checkpoint
    Missing | Accepted | Finalized
```

No one state is inferred from another. Reconciliation reads each authority and
validates the links.

### 6.2 Attempt transition table

| From | Operation | To | Guard |
|---|---|---|---|
| Acquired | PreparePreDispatchIntent | PreDispatchPending | exact live lease + claimed approval |
| PreDispatchPending | repeat intent | same | complete intent equal |
| PreDispatchPending | publish valid budget denial | Abandoned | authoritative no reservation + stable denial receipt |
| PreDispatchPending | bind reservation | PreDispatchReady | exact reservation recovered by Attempt identity |
| PreDispatchReady | repeat reservation bind | same | complete reservation equal |
| PreDispatchReady | bind receipt | PreDispatchAccepted | exact Accepted checkpoint and receipt |
| PreDispatchAccepted | repeat bind | same | same AuditId/receipt |
| PreDispatchAccepted | mark dispatch | DispatchStarted | exact current fencing + receipt + reservation |
| PreDispatchPending | reconcile no reservation/checkpoint | Abandoned | both authoritative Missing; dispatch provably false |
| PreDispatchPending | reconcile recovered reservation | PreDispatchReady | exact reservation; then close or same-Worker continue |
| PreDispatchReady | reconcile authoritative Missing checkpoint | Abandoned | dispatch provably false; reservation Released |
| PreDispatchAccepted | reconcile no-dispatch | ReleasePending | dispatch provably false; reservation Released |
| ReleasePending | finalize/publish | Released | exact Released audit when checkpoint exists |
| Pending/Ready/Accepted | authority unavailable | Indeterminate/fenced | no release, abandon, replacement, or dispatch |
| any pre-dispatch | stale/conflicting identity | unchanged | Conflict |

`Indeterminate` is not a license to discard the linked Attempt. The provider
retains its pre-dispatch substate and receipts for reconciliation.

### 6.3 Acquire behavior

For the same fingerprint:

| Existing state | Acquire result |
|---|---|
| active Acquired before Prepare | InProgress until ordinary lease rules resolve |
| PreDispatchPending, any lease expiry | InProgress/Indeterminate; never new Attempt |
| PreDispatchReady, any lease expiry | InProgress/Indeterminate; never new Attempt |
| PreDispatchAccepted, any lease expiry | InProgress/Indeterminate; never new Attempt |
| ReleasePending | InProgress |
| Abandoned denial receipt | a later same-fingerprint Acquire creates a new Attempt |
| Released | a later Attempt may acquire |
| Completed | Completed replay |
| post-dispatch Indeterminate | Indeterminate |

A different fingerprint remains Conflict in every state.

An Abandoned denial receipt is Attempt-scoped. Repeating/querying the old
Attempt returns the same safe denial receipt, while a new Acquire for the same
logical key and fingerprint creates a new Attempt and evaluates current policy
and capacity again. The logical invocation does not replay the denial as
Completed.

## 7. Protocols

### 7.1 First acceptance

```text
1. Acquire exact invocation lease.
2. Evaluate and claim approval.
3. PreparePreDispatchIntent in Gate.
4. Reserve budget idempotently by pre-dispatch Attempt identity.
5. Bind the exact reservation in Gate and confirm Ready.
6. Record complete checkpoint.
7. Require Accepted or Duplicate with exact receipt.
8. Bind receipt in Gate.
9. Confirm Gate returns the same Accepted binding.
10. Mark DispatchStarted using lease + receipt + ReservationId.
11. Only then call Dispatcher.
```

Conflict, invalid provider results, or any mismatch calls Dispatcher zero times.

### 7.2 Budget reserve response loss

A known valid Denied result (`Status=Denied`, null Reservation, non-empty stable
reason) publishes the Pending Attempt as `Abandoned` through one named
idempotent denial transition after Decision Audit handling. The Gate stores the
stable safe denial outcome/reason in the Attempt receipt. It creates no
pre-dispatch checkpoint, calls Dispatcher zero times, and permits no budget
finalization because no reservation exists.

The Gate Abandoned receipt is authoritative for Attempt terminal state and for
allowing a later same-fingerprint Acquire to create a new Attempt. Governance
Decision Audit is authoritative evidence for the denial reason when accepted;
Required Decision Audit failure changes the safe returned denial/audit outcome
but cannot turn a confirmed no-reservation denial into possible dispatch.

A malformed Denied result, a Denied result carrying a reservation, or an
exception is not proof that no reservation committed. Those paths use the
Attempt-identity query below and remain fenced while the result is unavailable.

When Reserve throws after a possible commit, Pending already fences the
Attempt. The Invoker queries the budget by `AgentToolPreDispatchIdentity`:

- Reserved + complete equivalent request: bind the original ReservationId and
  continue only under the same live ownership rules;
- authoritative Missing: retry the same reserve once while ownership remains
  exact, then query again after any second ambiguity;
- changed request, incompatible terminal state, unavailable/invalid lookup:
  remain fenced and return `Indeterminate`.

A restarted reconciler may recover the reservation by Attempt identity but
never uses that fact to dispatch. It releases/closes the Attempt when safe.

### 7.3 Reservation-bind response loss

When the ReservationId is known but Gate Ready acknowledgement is lost, the
Invoker reads the Gate by pre-dispatch identity:

- exact Ready binding: continue to Record;
- Pending: retry the same reservation bind once, then query again;
- conflicting Ready/Accepted state: Conflict;
- unavailable/unknown: remain fenced.

The Auditor is never called before exact Ready confirmation.

### 7.4 Immediate Record response loss

When Record throws after a possible commit:

```text
GetPreDispatchState(identity)
```

- Accepted + complete equivalent checkpoint:
  bind the returned original receipt; continue only under INV-11.
- Accepted + different checkpoint:
  Conflict; remain fenced.
- authoritative Missing:
  the same Worker may retry the same Record once while ownership and Reserved
  budget remain exact; any second ambiguity remains fenced.
- lookup unavailable/invalid:
  remain fenced and return `Indeterminate`.

Record retry is not the recovery identity. It is a bounded same-Worker action
after authoritative Missing. Durable lookup is the recovery authority.

### 7.5 Receipt-bind response loss

When the Auditor receipt is known but Gate binding acknowledgement is lost:

```text
Gate.GetPreDispatchState(identity)
```

- exact Accepted binding: continue under INV-11;
- Ready: retry the same bind once, then query again;
- conflicting Accepted binding: Conflict;
- unavailable/unknown: remain fenced.

Dispatcher is never called before exact bind confirmation.

### 7.6 Restart or asynchronous reconciliation

The fixed order is:

```text
1. Read Gate Attempt by exact tenant/logical/Attempt identity.
2. Reject Missing, stale, post-dispatch, or already incompatible state.
3. Read the budget reservation by the same Attempt identity.
4. Recover/bind the exact reservation when one exists.
5. Read governance checkpoint from the authoritative provider.
6. If Accepted, compare the complete checkpoint to Gate/Attempt context.
7. Prove DispatchStarted == false.
8. Idempotently settle Reserved to Released, or confirm already Released.
8a. Accepted checkpoint:
      PrepareRelease(AuditId, ReservationId)
      Finalize governance checkpoint as Released
      PublishRelease
8b. authoritative Missing checkpoint:
      AbandonUnrecordedLease through the reconciliation-safe fenced transition
9. Persist/return the reconciliation observation; create an immutable receipt
   only for a terminal result. StillPending updates retryable observation
   metadata and remains eligible to progress.
10. Publish best-effort Accountability fact after the control transition.
```

The reconciler does not call approval evaluation and does not dispatch. Approval
facts are compared only to prove that the accepted checkpoint belongs to the
same Attempt.

### 7.7 Authoritative Missing

Missing means the primary authority completed a consistent lookup and no row
exists while retention is guaranteed. Only then may reconciliation close an
unrecorded pre-dispatch Attempt.

Budget Missing is interpreted with the durable Gate state:

| Gate state | Budget | Checkpoint | Result |
|---|---|---|---|
| PreDispatchPending | authoritative Missing | authoritative Missing | Abandon unrecorded Attempt when dispatch is proven false |
| PreDispatchReady | authoritative Missing | any | Conflict because a ReservationId was already bound |
| PreDispatchAccepted | authoritative Missing | Accepted | Conflict because the accepted checkpoint binds a reservation |

There is no third “stronger Missing” status. The strength comes from the
authoritative read contract plus the Gate/checkpoint composition, not from a
provider-specific absence value.

Missing cannot be produced from:

- a timeout or cancellation;
- a caught provider exception;
- an eventually consistent replica;
- a cache miss;
- an unknown migration/schema version;
- a cleanup result without a linked terminal receipt;
- a query that omitted tenant scope.

### 7.8 Accepted checkpoint with Released budget

This is expected after the current Worker fenced an ambiguous pre-dispatch
write. Reconciliation validates the original ReservationId and confirms the
stored terminal state is Released with the expected reason family. It then
finalizes/publishes the Attempt as Released. It does not create a new budget
reservation and does not dispatch.

### 7.9 Accepted checkpoint with Reserved budget

Across restart, the reconciler releases it and closes the Attempt. It does not
resume execution. Within the same live call only, INV-11 permits the Invoker to
bind the receipt and proceed to dispatch.

### 7.10 Incompatible budget state

- Committed while Gate proves no DispatchStarted: Conflict; do not rewrite.
- Indeterminate: remain `StillPending`/Indeterminate.
- `PreDispatchPending` + authoritative Budget Missing + authoritative
  Checkpoint Missing + `DispatchStarted == false`: publish/confirm the
  unrecorded Attempt as Abandoned. This is the absence-proof path.
- `PreDispatchReady` + bound ReservationId + Budget Missing: Conflict; do not
  erase the binding or abandon the Attempt.
- `PreDispatchAccepted` + accepted Checkpoint + Budget Missing: Conflict; do not
  finalize, release, or dispatch.
- different ReservationId/Attempt/fingerprint: Conflict.

### 7.11 Post-dispatch states

If Gate reports DispatchStarted, CompletionPending, Completed, or cannot prove
that dispatch did not start, the pre-dispatch reconciler returns
`PostDispatchUnknown` or the existing terminal state. It never infers the Tool
result and never releases a committed/indeterminate budget.

### 7.12 Cancellation

Caller cancellation stops waiting but does not roll back a possible durable
transition. Cleanup/reconciliation uses its own bounded operational token.
Cancellation at every write boundary is tested as an acknowledgement-loss
window, not interpreted as proof of no commit.

## 8. Crash Window Ledger

Every row is a required executable case. “Worker action after restart” never
means dispatch.

| ID | Crash/response-loss point | Durable facts that may exist | Required recovery |
|---|---|---|---|
| CW01 | before Pending-intent commit | lease; no budget request may start | ordinary lease rules; no false checkpoint/budget claim |
| CW02 | after Pending commit, before Reserve | Pending; budget Missing | authoritative Missing budget/checkpoint -> abandon |
| CW03 | during Reserve before commit/response | Pending; budget unknown | query reservation by Attempt; never open replacement |
| CW04 | after Reserve commit, before response | Pending + Reserved budget | recover original ReservationId by Attempt identity |
| CW05 | after reservation response, before Gate bind | Pending + Reserved budget | bind exact reservation or reconcile Released |
| CW06 | after Ready bind commit, before response | Ready + Reserved budget | Gate lookup recovers Ready binding |
| CW07 | during Record before commit | Ready; checkpoint unknown | lookup; Missing or Accepted, never guess |
| CW08 | after checkpoint commit, before response | Ready + Accepted checkpoint | recover original receipt by Attempt identity |
| CW09 | after receipt response, before Gate bind | Ready + Accepted checkpoint | bind exact receipt or reconcile Released |
| CW10 | after Accepted bind commit, before response | Accepted Gate + checkpoint | Gate lookup recovers binding |

```text
    optional immutable terminal receipt: terminal status/terminal-at/integrity
```

Host scope uses the Phase 9b explicit non-null scope representation. All keys,
queries, unique constraints, and foreign keys begin with exact tenant scope.

### 9.4 Transaction and CAS rules

- First checkpoint insert is conditional on exact identity absence.
- Duplicate/conflict reads the existing complete snapshot in the same
  transaction/locking discipline used to classify the write.
- Gate prepare/bind/dispatch transitions use revision or conditional-state CAS.
- A failed CAS is re-read and classified; it is never blindly retried as a
  delegate.
- Same-database participants may use the Phase 9b transaction coordinator, but
  public correctness does not claim a cross-provider distributed transaction.
- COMMIT acknowledgement loss is reconciled by read; the mutation delegate is
  not automatically replayed.
- Database constraint/provider failures translate to stable provider-neutral
  contract outcomes or persistence exceptions.

### 9.5 In-memory support tier

Development in-memory Gate, Budget, and Auditor pass all semantic Contract Cases:

- identity, snapshot, duplicate/conflict;
- Pending/Ready/Accepted fences;
- stale fencing rejection;
- concurrent identical Record;
- concurrent reconciliation;
- idempotent budget/release behavior.

They do not run restart/crash/migration/database AOT cases and must keep their
existing explicit volatile documentation.

## 10. Retention and Cleanup

### 10.1 Retention inputs

The production composition declares at least:

```text
MaximumInvocationReconciliationWindow
InvocationAttemptReceiptRetention
BudgetReservationRetention
GovernanceCheckpointRetention
GovernanceFinalizationRetention
ReconciliationObservationRetention
ReconciliationReceiptRetention
AccountabilityProjectionRetryWindow
```

Startup validation requires every participant retention to cover the maximum
window in which another participant can still refer to it. A shorter value is a
startup error, not a warning.

### 10.2 Cleanup eligibility

Cleanup may remove an aggregate only when all are true:

1. the logical invocation is in a published terminal state;
2. no Attempt is PreDispatchPending, PreDispatchReady, PreDispatchAccepted,
   ReleasePending, CompletionPending, or Indeterminate;
3. all linked budget reservations are terminal;
4. governance finalization is terminal when a checkpoint exists;
5. any terminal reconciliation receipt is older than the maximum window, and
   no retryable StillPending observation remains live;
6. no active reconciliation lease/revision exists;
7. Accountability retry policy no longer needs the source fact;
8. one transaction/CAS proves the rows are still eligible.

The provider does not delete a checkpoint merely because `AcceptedAt` is old.

### 10.3 Lookup and cleanup race

An authoritative lookup and cleanup must share a locking/version protocol such
that a live nonterminal row cannot disappear and become a false Missing. If
cleanup wins on an already terminal aggregate, the retained terminal
reconciliation receipt remains queryable for its declared window.

## 11. Accountability Projection

The reconciler may emit one safe post-fact `AuditEnvelope` after a control
transition. The producer is Agent Tools runtime and uses `IAuditRecorder`, never
`IAuditSink` directly.

Suggested semantics:

```text
Action.Kind = agent-tool.governance
Action.Name = pre-dispatch-reconciled
Target.Kind = agent-tool-attempt
Outcome     = succeeded | rejected | indeterminate
```

Safe references may include Tool/Capability descriptors, logical execution and
Invocation IDs, AttemptId, safe AuditId, and ReservationId. The projection does
not include arguments, prompt/content, opaque approval evidence, raw provider
error, SQL, or Tool output.

Ordering is fixed:

```text
durable governance transition
    -> durable reconciliation receipt
    -> best-effort Accountability projection
```

Projection failure leaves the first two results unchanged. Reliable retry of
the projection remains #25 unless a bounded producer-owned retry already exists.

## 17. Review Findings and Blind-spot Closure

### R01 — Caller-generated AuditId relocates the uncertainty window

Closed by Attempt-identity lookup and provider-issued receipt.

### R02 — Retry alone is not a restart protocol

Closed by a read-only durable lookup. Record retry is bounded and allowed only
after authoritative Missing in the same live ownership window.

### R03 — Lease expiry could expose a replacement Attempt

Closed by durable `PreDispatchPending` before budget reservation and Acquire
rules that retain Pending/Ready/Accepted fences across expiry/restart.

### R04 — Accepted checkpoint could exist before Gate knows its AuditId

Closed by separate Pending, Ready, and receipt-binding transitions plus
bind-response lookup.

### R05 — A checkpoint hash could hide omitted fields

Closed by complete snapshot equality and one mutation case per nested field.

### R06 — Missing could be manufactured from provider failure or replica lag

Closed by normative authoritative-Missing semantics and primary/consistent read
requirements.

### R07 — Restart recovery could accidentally become business replay

Closed by the hard same-Worker versus restarted-reconciler boundary. Reconciler
has no Dispatcher dependency.

### R08 — Budget may already be Released

Closed by independent read and idempotent terminal transition. Released is an
expected recovery input, not a reason to create a new reservation.

### R09 — DispatchStarted acknowledgement can also be lost

Closed by separating CW12/CW13. Only an exact durable false remains in this
pre-dispatch protocol; true/unknown is post-dispatch Indeterminate.

### R10 — Cleanup can turn Accepted into false Missing

Closed by linked-state retention, cleanup CAS, and retained terminal receipts.

### R11 — Accountability could be mistaken for authorization evidence

Closed by post-transition ordering and one-way producer dependency.

### R12 — In-memory tests could overclaim production durability

Closed by separate semantic and durable driver interfaces and no conditional
skip that treats InMemory as restart-capable.

### R13 — Migration defaults could weaken complete comparison

Closed by required format version, generated deserialization, and fail-closed
missing-field/incompatible-schema cases.

### R14 — Cross-tenant identity collision

Closed by exact tenant prefix on all API/SQL identities and host/two-tenant
contract cases.

### R15 — Cross-provider atomicity could be implied

Closed by staged publication fences and idempotent reconciliation. One
PostgreSQL composition may use one transaction, but the public contract does
not claim distributed atomicity.

### R16 — Budget could commit before the pre-dispatch fence exists

Closed by persisting the Pending intent before Reserve, making Reserve
idempotent/queryable by Attempt identity, and adding a separate reservation-bind
transition before checkpoint Record. A lost ReservationId can no longer reopen
the Attempt or become undiscoverable after restart.

### R17 — Lease renewal could mutate checkpoint equality

Closed by freezing the lease snapshot returned from Pending-intent preparation
and storing current renewal expiry separately. Renewal preserves ownership but
cannot rewrite accepted evidence.

### R18 — Moving the fence before Reserve changes the Denied branch

Closed by an explicit no-reservation transition from Pending to an immutable
Attempt-scoped Abandoned denial receipt. Malformed/ambiguous denial uses Attempt
lookup and remains fenced until absence or a reservation is authoritative.

### R19 — A partial durable provider would preserve a volatile split path

Closed by requiring complete PostgreSQL Gate/Budget/Auditor implementations and
the existing Phase 8f contract suites. Only post-dispatch reconciliation logic,
not post-dispatch state durability, remains outside #70.

### R20 — Budget Missing had two incompatible meanings

Closed by keeping one authoritative Missing contract and interpreting it with
the Gate state. Pending + Budget Missing + Checkpoint Missing may abandon when
dispatch is false; Ready or Accepted plus Budget Missing is Conflict.

### R21 — Accepted receipt binding named the wrong source state

Closed by requiring `BindAcceptedPreDispatch` to transition only an exact
`PreDispatchReady` Attempt. Pending must bind its reservation first.

### R22 — Retention omitted PreDispatchReady

Closed by using one non-cleanable set everywhere: PreDispatchPending,
PreDispatchReady, PreDispatchAccepted, ReleasePending, CompletionPending, and
Indeterminate. Cleanup has a direct Ready-state case.

### R23 — Valid Budget Denied had no frozen terminal semantics

Closed by publishing an Attempt-scoped Abandoned denial receipt. The Gate
receipt owns Attempt terminal/reacquire semantics; Governance Decision Audit
owns accepted denial evidence. Same-fingerprint Acquire creates a new Attempt,
while repeated denial publication returns the original receipt.

### R24 — StillPending was conflated with a terminal receipt

Closed by separating retryable reconciliation observations from immutable
terminal receipts. StillPending metadata may advance and later become Released;
it cannot permanently terminalize the reconciler.

## 19. Exit Criteria

Issue #70 is complete only when:

1. Direction 2 is the only public recoverability contract.
2. All normative Case IDs and test names exist and the traceability ledger is
   executable in Boundary CI.
3. InMemory passes every semantic Contract Case without claiming durability.
4. PostgreSQL passes the same semantic cases plus restart, crash, migration,
   retention, tenant, concurrency, and native cases.
5. Identical retry and concurrent retry return one original receipt.
6. Every complete-checkpoint mutation conflicts and preserves the first row.
7. Pending, Ready, and Accepted states survive expiry/restart and block
   replacement.
8. Same-Worker immediate recovery dispatches at most once and only with exact
   accepted proof.
9. Restart reconciliation never dispatches and safely closes only proven
   pre-dispatch Attempts.
10. Authoritative Missing cannot be manufactured from failure, lag, cleanup, or
    omitted tenant scope.
11. Budget and Gate transitions are idempotent under response loss and
    concurrent reconcilers.
12. Post-dispatch true/unknown states remain outside pre-dispatch recovery.
13. Accountability projection is safe, post-fact, and non-authoritative.
14. Cleanup cannot remove live reconciliation evidence.
15. Runtime dependency boundaries expose no provider types.
16. Generated JSON is the only durable serialization path.
17. A real PostgreSQL crash worker proves the original checkpoint and receipt
    survive process death.
18. A real linux-x64 NativeAOT binary executes the provider mainline and prints
    `CRESTCREATES_DURABLE_AGENT_TOOL_PREDISPATCH_OK`.
19. `memory.md` records the support tier only after the executable evidence is
    available.
20. No document or test claims automatic business replay or exactly-once
    external side effects.
21. Pending + authoritative Budget/Checkpoint Missing can close an unrecorded
    Attempt, while Ready/Accepted + Budget Missing is Conflict.
22. Accepted receipt binding can transition only from PreDispatchReady.
23. Retention and cleanup protect Pending, Ready, Accepted, ReleasePending,
    CompletionPending, and Indeterminate with one consistent state set.
24. Valid Budget Denied produces one Attempt-scoped Abandoned receipt; later
    same-fingerprint Acquire creates a new Attempt rather than replaying denial
    as logical completion.
25. StillPending remains a retryable observation and can progress to one
    immutable terminal reconciliation receipt.
